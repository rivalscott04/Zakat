# CLAUDE.md

# ZAKAT OS — AI DEVELOPMENT CONSTITUTION

This document defines the mandatory operating rules for any AI agent or developer working on ZETRA.

This document is the primary development instruction for the repository.

All AI agents and developers MUST follow these rules when creating, modifying, deleting, refactoring, reviewing, or proposing any part of the system.

Do not treat these rules as suggestions.

---

# 1. PRIMARY PRINCIPLE

ZETRA is developed based on the Product Requirement Documents located in:

/docs

The PRD documents are the primary source of truth for the system.

Before creating or modifying anything, always review the applicable PRD documents.

The AI or developer MUST NOT implement features based only on assumptions, personal preferences, existing code, or technical convenience.

The required decision hierarchy is:

PRD
>
Approved User Decision
>
Existing Architecture
>
Existing Code
>
AI Assumption
>
Personal Preference

If existing code conflicts with the PRD, do not automatically assume the existing code is correct.

Analyze the conflict first.

If a product, business, security, architectural, or domain decision is required, stop and ask the user.

# 2. CORE PRD FIRST RULE

Before working on ANY feature, module, bug fix, refactor, migration, API, UI, service, model, database structure, security rule, permission, integration, or performance improvement:

ALWAYS read the Core PRD first.

The Core PRD is the foundation and constitution of ZETRA.

No module implementation may violate the Core PRD.

Mandatory reading order:

1. Core PRD.
2. Relevant Cross-Cutting PRD.

# 3. PRD HIERARCHY

ZETRA uses a hierarchical PRD structure.

The hierarchy is:

1. Core PRD.
2. Cross-Cutting PRD.
3. Module PRD.
4. Feature Requirement.
5. Implementation Detail.

Priority order:

Core PRD
>
Cross-Cutting PRD
>
Module PRD
>
Feature Requirement
>
Implementation Decision

Higher-level rules override lower-level rules.

If two PRDs conflict:

DO NOT silently choose one.

DO NOT automatically modify the implementation.

STOP.

Explain:

1. Which documents conflict.
2. Which requirements conflict.
3. The impact of each option.
4. The recommended solution if applicable.

Then ask the user for a decision.

# 13. WHEN TO STOP AND ASK THE USER

The AI MUST stop and ask the user before implementation when:

- A PRD conflicts with another PRD.
- A business rule is missing.
- A financial rule is unclear.
- A security decision changes system behavior.
- A new role is required.
- A new permission is required.
- A new status is required.
- A new workflow is required.
- A database change changes the domain model.
- A suggestion changes the PRD.
- Existing code conflicts with the documented architecture.
- Multiple modules are affected unexpectedly.
- A destructive migration is required.
- Existing data must be transformed.
- A product decision is required.
- The AI would otherwise need to guess.

The AI must never silently make these decisions.

# 18. THIN CONTROLLER RULE

Controllers must remain thin.

Controllers are responsible for:

- Receiving requests.
- Calling validation.
- Calling services.
- Returning responses.

Controllers must NOT contain:

- Complex business logic.
- Financial calculations.
- Complex workflow.
- Database transaction logic.
- Large loops.
- Approval logic.
- Ledger logic.
- Fund movement logic.

Business logic belongs in the Service Layer.

---

# 19. FORM REQUEST RULE

Primary request validation must use Laravel Form Requests.

Examples:

StoreMuzakkiRequest.

UpdateMuzakkiRequest.

StoreCollectionRequest.

ApproveDistributionRequest.

ConfirmPaymentRequest.

Frontend validation is allowed for user experience.

Frontend validation is NOT a security mechanism.

Backend validation is mandatory.

---

# 20. SERVICE LAYER RULE

Business logic belongs in Services.

Examples:

CollectionService.

DistributionService.

FundService.

LedgerService.

AssessmentService.

ProgramService.

PaymentService.

ReconciliationService.

NotificationService.

Services are responsible for:

- Business rules.
- Workflow.
- Calculation.
- State transition.
- Database transaction.
- Domain validation.
- Integration orchestration.

---

# 21. API RESOURCE RULE

API responses should use Laravel API Resources where applicable.

Resources are responsible for:

- Data transformation.
- Response structure.
- Controlled field exposure.
- Relationship transformation.

Resources MUST NOT execute additional database queries.

All required relationships must be loaded before the Resource is created.

---

# 22. NO N+1 QUERY RULE

N+1 queries are not allowed.

Before returning a collection:

Identify all relationships required by:

- API Resource.
- Frontend.
- Business logic.

Use eager loading where required.

Example:

with([
    'muzakki',
    'fund'
])

Do not query relationships inside loops.

Do not query relationships inside API Resources.

Do not use lazy loading as an excuse for missing query planning.

---

# 23. QUERY PERFORMANCE RULE

For list endpoints:

Use pagination.

Do not use:

Model::all()

for potentially large production datasets.

Use:

paginate().

simplePaginate().

cursorPaginate().

as appropriate.

Use select() when the entire model is not required.

Load only required relationships.

Do not over-fetch data.

---

# 24. DATABASE TRANSACTION RULE

Any operation that modifies multiple related records and must succeed as a single unit must use a database transaction.

Examples:

Distribution execution:

- Update distribution.
- Update fund.
- Create ledger entry.
- Create audit event.

All must succeed.

If one fails:

Everything must rollback.

# 25. SECURITY PRINCIPLE

All implementation must follow:

22-security.md

Mandatory principle:

NEVER TRUST THE FRONTEND.

The frontend is not the source of truth.

The backend must validate:

- Authentication.
- Authorization.
- Organization scope.
- Object access.
- Current state.
- Allowed state transition.
- Business rules.
- Financial state.
- Current database state.

Do not trust:

- Hidden fields.
- Disabled inputs.
- Frontend roles.
- Frontend permissions.
- user_id.
- organization_id.
- status.
- balance.
- approved_by.
- amount without validation.
- calculated values without server verification.

---

# 26. BACKEND SOURCE OF TRUTH

For sensitive operations, the backend determines:

Authenticated User.

Organization Context.

Permission.

Current Object State.

Allowed Action.

Current Balance.

Available Fund.

Final Amount.

Approval Authority.

Transaction State.

# 27. IDOR AND BOLA PROTECTION

Every object accessed through:

- ID.
- UUID.
- Code.
- Reference Number.
- Slug.
- Any identifier.

must have object-level authorization.

Never assume authentication means object access authorization.

Incorrect:

Model::findOrFail($id);

without checking access.

Required concept:

Authenticated User

+

Permission

+

Organization Scope

+

Object-Level Authorization.

---

# 28. ORGANIZATION ISOLATION

Organization boundaries are mandatory.

Never trust organization_id directly from the frontend.

Every organization-scoped query must verify the current organization context.

Cross-organization access requires explicit authorization.

Users must never gain access to another organization's data by modifying:

organization_id.

resource_id.

URL parameters.

API payload.

---

# 29. IDEMPOTENCY RULE

Sensitive transactional operations must be idempotent or otherwise protected against duplicate processing.

Examples:

- Payment creation.
- Payment confirmation.
- Collection recording.
- Distribution execution.
- Fund transfer.
- Ledger posting.
- Refund.
- Reversal.
- Webhook processing.
- External callback.

Do not assume:

The user clicks once.

The browser sends once.

The network never retries.

The external provider sends once.

Duplicate protection must be implemented where required.

---

# 30. CONCURRENCY RULE

Financial and balance-changing operations must be concurrency-safe.

Evaluate:

- Race condition.
- Double spending.
- Concurrent request.
- Duplicate execution.
- Stale balance.

Use when appropriate:

- Database transactions.
- Row locking.
- Atomic update.
- Unique constraints.
- Idempotency.
- Queue serialization.

Never implement a financial operation that can produce inconsistent balances under concurrent requests.

---

# 31. DATABASE CONSTRAINT RULE

Application validation is not sufficient for critical data integrity.

Use database-level protection where appropriate:

- Unique constraints.
- Foreign keys.
- Indexes.
- Database transactions.

For critical unique identifiers, database uniqueness is required.

Examples may include:

- External transaction ID.
- Gateway transaction ID.
- Webhook event ID.
- Reference number where uniqueness is required.

---

# 32. FINANCIAL SECURITY RULE

Frontend values are never the final source of truth for:

- Fund balance.
- Available balance.
- Ledger balance.
- Final allocation.
- Final distribution amount.
- Approval amount.
- Remaining fund.

The backend must retrieve the current state and validate the operation.

Never use float for money calculations.

Use the monetary representation defined by the Core PRD and related financial modules.

---

# 33. STATE TRANSITION RULE

Status transitions must be controlled by backend logic.

The frontend must not directly set arbitrary sensitive status values.

Incorrect concept:

PATCH /distribution/1

{
    "status": "EXECUTED"
}

Instead use explicit business actions where appropriate:

approve().

reject().

execute().

cancel().

reverse().

The backend must verify:

Current State.

Allowed Transition.

Authorization.

Business Rule.

---

# 34. MASS ASSIGNMENT RULE

Do not use:

$request->all()

directly for sensitive persistence.

Use:

$request->validated()

Then explicitly map sensitive fields where appropriate.

Never allow clients to mass assign:

organization_id.

user_id.

role.

permission.

status.

approved_by.

created_by.

updated_by.

balance.

ledger_balance.

financial totals.

unless explicitly handled by secure backend business logic.

---

# 35. WEBHOOK SECURITY RULE

External webhooks must not be trusted automatically.

When supported by the provider:

Verify:

- Signature.
- Timestamp.
- Event ID.
- Provider identity.
- Duplicate event.

Webhook processing must consider:

Idempotency.

Replay protection.

Duplicate protection.

Heavy processing should be queued when appropriate.
